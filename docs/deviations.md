### DEV-02 — Включение CLEAR_MEASURED и кандидат CLR

- Дата: 2026-10-23
- Требование: MAP-13 (таблица 5.3, «если включено»), раздел 15 (`AMBIENT_CLEAR_MAX` = 0 — «CLEAR_MEASURED выключено»)
- Суть: ТЗ не задаёт явный флаг включения CLEAR_MEASURED и не определяет, когда зона «валидна и цели до `max_distance` нет».
  Единственная подсказка — `AMBIENT_CLEAR_MAX = 0` означает «выключено».
- Варианты:
  1. Кандидат CLR — строго по 5.3, независимо от включения: все сообщённые цели зоны валидны (MAP-03) и каждая дальше `max_distance`
     (или целей нет); валидная цель ближе `MIN_DIST_CM` или с `distance_mm ≤ 0` даёт INV. `AMBIENT_CLEAR_MAX = 0` — CLEAR_MEASURED
     выключен, и подтверждённый CLR переводит OCCUPIED в UNKNOWN (строка таблицы «иначе UNKNOWN»); `> 0` — включён, и пустая зона
     даёт CLR, только если `ambient_per_spad ≤ AMBIENT_CLEAR_MAX`.
  2. Кандидат CLR возможен только при включённом CLEAR_MEASURED (первая редакция E1a). Тогда строка «иначе UNKNOWN» недостижима,
     и любое снятие препятствия идёт через `HOLD_MAX_MS` (500 мс вместо 3 кадров) с событием HOLD_EXPIRED.
- Рекомендация агента: вариант 1 — так написано в ТЗ; его предложил независимый проверяющий, реализовано после проверки
  (`classify_zone` в `core/src/fusion.c`, `cell_cfg_from_params`). **Риск для решения человека:** при выключенном CLEAR_MEASURED
  ограничения по засветке нет, поэтому зоны, «опустевшие» на солнце, снимают препятствие через 3 кадра (≈ 200 мс), а не через 500 мс.
  Для ArduPilot CLR и UNKNOWN неразличимы (max + 1 и 65535 — «нет данных»). Проверить на T-20.
- Решение человека: принято 2026-10-23: ТЗ 5.6, MAP-13a. При выключенном CLEAR_MEASURED CLR — только от валидной цели дальше max_distance, зона без цели — INV; при включённом — CLR только при ambient ≤ AMBIENT_CLEAR_MAX. Реализовано: `classify_zone` (`core/src/fusion.c`); риск засветки из этой записи снят.

### DEV-03 — «Доля валидных зон» для DEGRADED

- Дата: 2026-10-23
- Требование: MAP-10
- Суть: не определено, считается ли валидной зона без обнаруженных целей (`nb_target_detected = 0`). Если нет — датчик, смотрящий
  в открытое пространство, станет DEGRADED.
- Варианты:
  1. Зона валидна, если целей нет или хотя бы одна цель валидна по MAP-03; кадры, которых нет (датчик молчит, идёт переинициализация),
     считаются долей 0 с момента последнего кадра.
  2. Зона валидна, только если есть валидная цель.
- Рекомендация агента: вариант 1. Реализовано: `quality_zone_eval` (`zone_valid`), `sh_on_frame`, `mark_no_data` в
  `core/src/sensor_health.c`. Риск: засветка, гасящая все цели, по варианту 1 не делает датчик DEGRADED — проверить на T-20.
- Решение человека: принято 2026-10-23: ТЗ 5.6, MAP-10a — доля считается только по зонам с целью; дополнительно DEGRADED по медиане ambient > `AMBIENT_DEGRADED` (по умолчанию 0 — выключено до T-20). Реализовано: `fusion_push_frame`, `sh_on_frame(…, ambient_high, …)`.

### DEV-04 — Высота точки h_p и смещение датчика t_m

- Дата: 2026-10-23
- Требование: 5.1 (`p_L = R_y(θ) R_x(φ) p_B`, `h_p = h_tof − z_L`), MAP-15 (h_tof — дальномер «с пересчётом на точку установки датчиков»)
- Суть: если z_L брать от `p_B`, включающего `t_m`, вертикальное смещение датчика учитывается дважды: h_tof уже отнесена к точке датчика.
- Варианты:
  1. z_L — вертикальная составляющая луча от датчика: `z_L = [R_y(θ) R_x(φ) R_bs p_S]_z` (без t_m).
  2. Буквально по формуле с t_m; тогда h_tof надо отнести к началу корпусной СК, что противоречит MAP-15.
- Рекомендация агента: вариант 1. Реализовано: `geo_point_height` в `core/src/geometry.c`. d и ψ (MAP-04) считаются с t_m, строго по 5.1.
- Решение человека: принято 2026-10-23: ТЗ 5.6, MAP-14a — вариант, противоположный рекомендации: все высоты от центра корпуса, h_p = h_body − z_L(p_B) с t_m. Реализовано: `geo_point_height`, `geo_body_height_from_sensor`, `geo_body_height_from_rf`; источник h_body по фазам (дальномер через mavlink_rx) — E1b.

### DEV-05 — Угловая протяжённость зоны без параллакса t_m

- Дата: 2026-10-23
- Требование: MAP-02 («угловая протяжённость зоны хранится»), MAP-05
- Суть: протяжённость хранится как свойство зоны (направления лучей, повёрнутые в корпусную СК); сдвиг t_m от начала корпусной СК
  смещает видимый азимут на ≈ t_⊥ / r. При t_⊥ = 3 см это 1,7° на 1 м и 3,4° на 0,5 м — больше `CAL_TOL_DEG` = 2°.
- Варианты:
  1. Протяжённость по направлениям (сейчас); погрешность закрывается `CAL_TOL_DEG` на дальностях ≳ 1 м.
  2. Протяжённость для каждой цели на её дальности с учётом t_m (≈ 8 преобразований на цель).
- Рекомендация агента: вариант 1 до получения чертежа (`MOUNT_XYZ_M`, HW-07); при t_⊥ > 2 см — перейти на вариант 2. Реализовано:
  `geo_zone_extent` (сетка 5 × 5 по зоне), `fusion_init`.
- Решение человека: принято 2026-10-23: ТЗ 5.6, MAP-05a — вариант 2 независимо от величины смещения. Реализовано: `geo_zone_extent_at_range`, `mark_target`; для зон без цели в диапазоне (CLR/INV) используется протяжённость по направлениям.

### DEV-06 — Признак угловой достоверности; DEGRADED-датчик

- Дата: 2026-10-23
- Требование: 5.3 (ячейка хранит «признак угловой достоверности»), MAP-10 («ячейки неисправного датчика обрабатываются как INV»)
- Суть: (а) смысл признака угловой достоверности не определён; (б) не сказано, «неисправный» — это только FAILED или и DEGRADED.
- Варианты:
  1. (а) признак = протяжённость зоны-источника попадает в сектор без допуска `CAL_TOL_DEG`; (б) INV — только FAILED; данные DEGRADED
     обрабатываются как обычно (невалидные зоны и так INV по MAP-03).
  2. (б) DEGRADED тоже INV — тогда датчик с половиной плохих зон перестаёт сообщать и реальные препятствия.
- Рекомендация агента: вариант 1 (отбрасывать валидные препятствия DEGRADED-датчика менее безопасно). Реализовано: `cell_input_t.angle_ok`,
  `fusion_t.sector_core`, `fusion_run`.
- Решение человека: принято 2026-10-23: закрыто ТЗ 5.6 без отдельного пункта; действует вариант 1. Признак угловой достоверности теперь считается по протяжённости цели на её дальности (MAP-05a).

### DEV-08 — FUSION_WINDOW_MS и запуск слияния

- Дата: 2026-10-23
- Требование: MAP-09, раздел 15 (`FUSION_WINDOW_MS` = «1,5 периода кадра»)
- Суть: стартовое значение выражено через частоту, которая сама параметр; правило «когда карта готова» не задано.
- Принято: `FUSION_WINDOW_MS = 0` — автоматически 1,5 × (1000 / `SENSOR_FREQ_HZ`) мс (100 мс при 15 Гц); > 0 — явное значение.
  Шаг слияния запускается, когда (а) свежие кадры есть у всех датчиков, кроме FAILED, или (б) самый старый свежий кадр ждёт ≥ окна,
  или (в) приходит следующий кадр датчика, у которого свежий кадр ещё не слит (иначе молчащий датчик блокирует карту).
  Кадры старше самого нового более чем на окно отбрасываются (счётчик `frames_late_total`).
  Датчик не в состоянии RUNNING (идёт переинициализация или FAILED) не ожидается. Метка времени кадра чуть позже `now_us`
  (ISR после чтения часов циклом) считается возрастом 0, без переполнения.
  **Следствие для MAP-12 (T-11):** при `SCHEDULE = STAGGERED` самый старый кадр ждёт остальные ≈ 1/3–2/3 периода (до ≈ 44 мс при 15 Гц),
  поэтому норма t3 − t1 ≤ 15 мс в этом режиме недостижима без смены правила (например, шаг слияния на каждый кадр). Решение — по T-04/T-11.
- Рекомендация агента: принять; уточнить окно по T-05.
- Решение человека: принято 2026-10-23: ТЗ 5.6, MAP-09a — SIMULTANEOUS по окну (правила этой записи остаются), STAGGERED — слияние на каждом кадре с последними кадрами остальных не старше VALID_DATA_MAX_AGE_MS, t1 = время кадра-триггера. Реализовано: `fusion_run_staggered`, `fusion_t.t1_us`; для SIMULTANEOUS t1 — самый старый использованный кадр.

### DEV-09 — Детали автомата MAP-13

- Дата: 2026-10-23
- Требование: MAP-13, таблица 5.3; MAP-09; 5.2 (STALE)
- Суть: таблица не задаёт ряд деталей.
- Принято (`core/src/cell_fsm.c`, `core/src/fusion.c`):
  - OCC на равной дистанции — как «ближе»: обновляет время, без ожидания;
  - после `DIST_RELAX_FRAMES` подтверждений «дальше» берётся ближайшая из подтверждающих дистанций (консервативно);
  - «дальше» без подтверждения — валидное измерение: перезапускает отсчёт `HOLD_MAX_MS`; CLR отсчёт не перезапускает;
  - время валидного измерения — `t_ready_us` кадра-источника; истечение удержания проверяется по текущему времени;
  - STALE (`VALID_DATA_MAX_AGE_MS` = 150 мс) проверяется при экспорте по времени самого старого вклада и действует, только когда
    данных нет вовсе; при поступающих INV-кадрах удержание длится до `HOLD_MAX_MS` = 500 мс.
  - OCC из более старого кадра другого датчика не переводит отсчёт удержания назад;
  - истечение `HOLD_MAX_MS` проверяется только на кандидате INV (по таблице); после долгой тишины первый CLR или «дальше» OCC ещё
    1–2 кадра экспортирует прежнюю дистанцию (консервативно).
- Рекомендация агента: принять.
- Решение человека: принято 2026-10-23: закрыто ТЗ 5.6; детали автомата сохраняются как описано.

### DEV-11 — Отложенные замечания независимой проверки E1a

- Дата: 2026-10-23
- Требование: MAP-13 («с записью в лог»), SW-07 (событие при умолчаниях), MAP-07

    Вариант: отклонять DROP в прошивке до явного решения человека.

- Решение человека: принято 2026-10-23: ТЗ 5.6, MAP-07a — DROP отвергается без флага сборки `TOF_ALLOW_GROUND_DROP` (по умолчанию 0; проверка сборкой `test_params_drop`); экспорт DROP в фазе FLIGHT — с MAP-17 в E1b. Запись в лог при истечении удержания и событие умолчаний — E1b (модуль `events`).
